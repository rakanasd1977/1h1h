## 7) Security sweep (auth/CSRF/RBAC/rate-limit) — audit result + what was fixed

**Status:** sweep completed. Two hardening fixes applied; three items remain as *deliberate design* until out-of-band delivery (email/SMS) is configured for production.

**Fixed (with tests):**
- **Token-purpose separation (critical cross-use):** verify and password-reset tokens previously shared the same `user_verifications` row and the same `WHERE token = ?` lookup — a verify token could reset a password, and a reset token could be consumed by `/auth/verify-email`, which issues a live session JWT. Migration `054` adds a `purpose` column; verify/confirm lookups now filter by purpose, and `forgot-password` never reuses a verify token. (`auth.ts`, tests in `forgot-password.test.js`.)
- **Lockout per (identifier+IP) pair (availability):** failures were counted per identifier across all IPs, so any attacker could lock any account with 5 failed logins from a single address. `lockout.ts` now locks the (identifier, ip) pair at the threshold, keeps the per-IP flood guard, and adds a distinct-IP threshold to still block distributed brute-force. (`lockout.ts`, tests in `security-auth.test.js`.)

**Deliberate design (documented, not changed — changing breaks product flow):**
1. `verification_token`/reset token returned in the API response (`auth.ts`, `register-customer`/`change-email`/`forgot-password`). There is **no configured email/SMS provider**, so the response is the only delivery channel the mobile UI and tests rely on. **Before production go-live:** configure `email`/`sms`/`app_base_url` settings, stop returning tokens in responses, and deliver out-of-band only, then remove this note.
2. Account enumeration via `409` on duplicate email/phone at registration, and the uniform-but-distinct `401` message. The UI depends on these to guide the user; acceptable for MVP (risk lower than #1 alone).
3. 2FA optional for privileged accounts and unavailable to customers (`PRIVILEGED_ROLES` only). Recommend: enforce TOTP enrolment for admin/agent/provider on creation, and offer TOTP to customers.

> Residual risk note: distributed DoS on the login lockout (many distinct IPs) still requires the attacker to reach the distinct-IP threshold; stop-loss is the existing route rate limit plus (recommended) nginx `limit_req`/WAF. The scan found no SQLi, no confirmed IDOR, and no JWT/CSRF flaws.
